# Protocol Former на русском

[English version](README.md)

Protocol Former — плагин для [Obsidian](https://obsidian.md), который помогает врачу-рентгенологу выполнять структурированные протоколы исследования прямо в рабочем хранилище. Плагин превращает протокол в пошаговый клинический сценарий: выберите нужную ветку, вставьте готовый текст или сниппет, повторите раздел для нескольких находок и добавьте сформированный текст в заметку, к которой привязана сессия.

Протоколы создаются как файлы **`.rp.json`** во встроенном визуальном редакторе.

## Для чего нужен Protocol Former

- **Стандартизация радиологических заключений.** Можно оформить локальные протоколы, алгоритмы по модальностям, рекомендации по follow-up или шаблоны структурированных заключений как дерево решений.
- **Пошаговые клинические ветвления.** Узлы вопросов и ответов помогают выбрать подходящий клинический путь без поиска по длинным статическим шаблонам.
- **Повторно используемые фрагменты текста.** Узлы сниппетов вставляют подготовленный текст из настроенной папки. Markdown-шаблоны могут запрашивать плейсхолдеры: свободный текст или выбор, которые заполняются во время выполнения протокола.
- **Повторяющиеся находки.** Узлы циклов подходят для нескольких очагов, узлов, измерений, анатомических уровней или других повторяемых разделов.
- **Работа поверх заметки.** Runner открывается как плавающая панель или как сессия в правой боковой панели, привязанная к активной Markdown-заметке, и добавляет выбранный текст протокола в эту заметку.
- **Визуальное создание протоколов.** Редактор протоколов поддерживает узлы старта, вопроса, ответа, сниппета и цикла, соединённые в граф. (Текстовые блоки из старых версий остаются поддерживаемыми — см. заметку о совместимости ниже.)

## Типичный клинический сценарий

1. Откройте или создайте Markdown-заметку для заключения.
2. Запустите команду **Run protocol** из палитры команд.
3. Выберите протокол из настроенной папки протоколов.
4. Ответьте на клинические вопросы в runner.
5. Заполните плейсхолдеры сниппетов, если они появятся.
6. Проверьте добавленный в заметку текст и при необходимости отредактируйте его перед финальным заключением.

Protocol Former помогает оформлять документацию. Клиническое решение, формулировки и финальная проверка заключения остаются ответственностью врача.

## Установка

Protocol Former работает только в настольной версии Obsidian.

### Через BRAT (рекомендуется)

1. Установите [Obsidian BRAT plugin](https://github.com/TfTHacker/obsidian42-brat).
2. В настройках BRAT выберите **Add Beta plugin** и вставьте GitHub URL этого репозитория.
3. Включите **Protocol Former** в списке Community plugins Obsidian.

### Ручная установка

1. Скачайте `main.js`, `styles.css` и `manifest.json` со страницы [GitHub Releases](https://github.com/vegacepticon/protocol-former/releases).
2. Скопируйте эти файлы в `<your-vault>/.obsidian/plugins/radiprotocol/`.
3. Перезагрузите Obsidian.
4. Включите **Protocol Former** в списке Community plugins.

> **Статус ребрендинга.** Видимое название плагина — **Protocol Former**. Идентификатор плагина, папка установки (`radiprotocol`), путь настроек, типы представлений, id команд и схема `.rp.json` пока сохраняют старое имя для совместимости, поэтому существующие установки и протоколы продолжают работать. Переименование id запланировано отдельным релизом с явной миграцией.

## Настройка

1. Откройте настройки Protocol Former.
2. Укажите **Protocol folder** — папку в хранилище, где лежат файлы протоколов `.rp.json`. По умолчанию `Protocols`; пустое значение отключает выбор протоколов.
3. Укажите **Snippet folder** — папку в хранилище, где лежат Markdown-сниппеты. По умолчанию `Snippets`.
4. Выберите разделитель накопленного текста заключения: новая строка или пробел.
5. При необходимости выберите язык интерфейса.
6. При необходимости включите **Run protocols in the right sidebar** и/или **Conclusion draft in runner**.

## Команды

Protocol Former добавляет следующие команды. Ни одна команда не имеет глобального хоткея по умолчанию.

| Команда | Что делает |
|---|---|
| **Run protocol** | Выбрать `.rp.json` и запустить сессию, привязанную к активной Markdown-заметке. Сессия открывается в плавающей панели или в правой боковой панели в зависимости от настройки. |
| **Start from specific node** | Выбрать протокол и стартовый узел, затем начать сессию с этого узла. Удобно для проверки отдельной ветки. Нужна активная Markdown-заметка. |
| **Open protocol editor** | Выбрать или создать `.rp.json` и открыть визуальный редактор. |
| **Insert snippet** | Выбрать сниппет и вставить его в позицию курсора активной Markdown-заметки; если редактор недоступен — добавить в конец заметки. |
| **Insert phrase from trigger** | Заменить слово перед курсором фразой в режиме вставки по хоткею. Назначьте хоткей в Settings → Hotkeys; фразам с автозаменой эта команда не нужна. |
| **Create snippet from selection** | Создать новый сниппет, взяв текущее выделение редактора как начальный шаблон. |
| **Open snippet manager** | Открыть менеджер сниппетов. |
| **Open community library** | Открыть библиотеку сообщества. |
| **Export protocol as library package** | Выбрать протокол и открыть окно экспорта: сохранить пакет в хранилище или отправить его в библиотеку сообщества. |
| **Open plugin menu** | Показать постоянное меню Protocol Former в правой боковой панели. |

Чтобы назначить хоткей, откройте **Settings → Hotkeys**, найдите команду по имени (например, `Run protocol`) и нажмите **+**. Obsidian хранит хоткеи отдельно для каждого хранилища.

### Клавиши внутри runner

Runner забирает фокус при открытии и возвращает его себе после каждого действия, поэтому следующая клавиша попадает в runner. Пока вы печатаете в заметке, фокус обратно не забирается. Ввод в текстовых полях не перехватывается. Буквы и цифры определяются по физической позиции клавиши, поэтому русская раскладка работает без переназначения, а компактная строка подсказок над кнопками показывает доступные сейчас сочетания.

| Клавиша | Действие |
|---|---|
| `1`–`9` | Выбрать соответствующий вариант: ответ, переход к вопросу, ветку сниппета, тело или выход цикла. Номер показан на каждом варианте. Вариант со свободным текстом переводит курсор в своё поле, а не отправляет его. |
| `Z` | Шаг назад. |
| `X` | Повторить отменённый шаг. |
| `S` | Пропустить текущий вопрос (когда у него есть готовые ответы). |
| `Backspace` | То же, что `Z`. |
| `Ctrl+←` или `Alt+←` | Шаг назад (старый вариант). |
| `Ctrl+→` или `Alt+→` | Повторить отменённый шаг (старый вариант). |
| `F` | Перейти в поле свободного ответа; если таких полей несколько — в первое пустое. |
| `C` | Перейти в черновик заключения. |
| `V` | Вставить черновик заключения в привязанную заметку. |
| `H` | Показать или скрыть строку подсказок. |
| `Esc` | Закрыть runner, когда фокус не в текстовом поле. Если в черновике заключения есть невставленный текст, Protocol Former спросит подтверждение. |
| `Ctrl+Space` | Отправить свободный ответ или подтвердить окно заполнения сниппета. Сочетание для одной руки: оно не вставляет символ, поэтому безопасно внутри поля. |
| `Shift+Enter` | Старый вариант `Ctrl+Space` в полях свободного ответа и в окне заполнения. |
| `Enter` | Добавить текущую строку как пункт черновика заключения. |
| `Shift+Enter` в черновике | Вставить перенос строки вместо добавления пункта. |
| `Tab` / `Shift+Tab` | Перейти к следующему/предыдущему элементу. |
| `j` / `k` / `Tab` / `Shift+Tab` | Перемещаться по результатам выбора сниппетов, когда фокус в списке. `Tab` с последней строки и `Shift+Tab` с первой выводят из списка к следующему элементу (с первой строки фокус возвращается в поле поиска). |

Нумеруются только первые девять вариантов шага; к остальным можно перейти клавишей `Tab` и мышью. Клавиши с `Ctrl`, `Alt` или `Cmd` остаются за Obsidian, кроме стрелок-алиасов и `Ctrl+Space`. Строка подсказок показывается по умолчанию: отключить её можно в **Settings → Protocol Former → Показывать строку подсказок в раннере**, там же открывается полная памятка по клавишам. Клавиша `H` по-прежнему переключает строку для текущей сессии.

В окне заполнения сниппета курсор сразу стоит в первом поле, так что первый `Tab` не нужен. Группа вариантов — одна остановка `Tab`: стрелки перемещают фокус между вариантами и кнопкой `✎` (свой вариант), `1`–`9` переключают вариант с этим номером, не покидая группу (номер показан на кнопке, а в текстовом поле цифры по-прежнему печатаются), а `Tab` выводит из группы к следующему полю. `Ctrl+Space` подтверждает вставку из любого места окна; `Shift+Enter` продолжает работать как старый вариант.

### Плавающая панель или правая боковая панель

Оба варианта используют один и тот же runner и один и тот же черновик заключения.

- **Плавающая панель (по умолчанию).** Runner — перетаскиваемая панель с изменяемым размером поверх заметки. Её позиция и размер запоминаются между сессиями. Одновременно может быть открыто несколько сессий для разных протоколов или заметок.
- **Правая боковая панель.** Включите **Run protocols in the right sidebar**. Для одной заметки создаётся не более одного runner: повторный запуск протокола для той же заметки показывает существующую сессию, а не открывает вторую вкладку. Чтобы начать новую сессию, закройте runner. При возврате к заметке, у которой есть runner, его вкладка показывается автоматически; если активная заметка отличается от привязанной, runner показывает кнопку **Focus note**.

Сессии runner временные: они не восстанавливаются после перезапуска Obsidian, а их состояние не сохраняется в настройках плагина.

## Черновик заключения

Под вариантами ответа в runner доступен временный черновик заключения. Введите строку и нажмите **Enter**, чтобы добавить отдельный пункт. Пункты можно редактировать, удалять и переставлять за ручку. В компактном блоке нет заголовка, пояснения и всплывающих подсказок; высота однострочного поля совпадает с высотой ручки, а длинный текст расширяет поле. Кнопка вставки расположена по центру.

Кнопка **Insert conclusion** вставляет весь черновик, включая ещё не подтверждённый ввод, в последнюю позицию курсора **в привязанной к runner заметке**. Заметка должна быть открыта в режиме редактирования. Пункты соединяются переводами строки, без заголовка и маркеров. После вставки они остаются в черновике; повторное нажатие вставляет весь текст ещё раз, не обновляя предыдущую вставку.

Переходы по протоколу, «Назад» и повтор шага не меняют черновик. С невставленным текстом завершение протокола или самопроверки не закрывает runner. Закрытие кнопкой runner, Escape вне текстового поля, крестиком вкладки или средней кнопкой мыши запрашивает подтверждение потери невставленного текста. Защита крестика зависит от интерфейса Obsidian; закрытие через команды/меню, выгрузка плагина и выход из приложения не перехватываются.

В протоколе можно задать **преднастроенный черновик заключения**. Откройте протокол в редакторе, нажмите кнопку с карандашом на плавающей панели и введите по одному пункту в строке. Эти пункты появятся в черновике сразу при запуске Runner для этого протокола и сохраняются в файле `.rp.json`. Нетронутый преднастроенный черновик считается стартовым шаблоном: он не мешает завершению протокола и не вызывает запрос подтверждения при закрытии. Любое изменение после запуска снова делает черновик невставленным.

Сам черновик сессии существует **только в текущем запуске**, не записывается в файл протокола или настройки и не восстанавливается после перезапуска. Функция включена по умолчанию; переключатель **Conclusion draft in runner** применяется к новым запускам.

## Текстовая автозамена

Protocol Former умеет вставлять длинный текст по короткому ключу, поэтому отдельные плагины Substitutions и Text Snippets больше не нужны. Вставка работает в полях свободных ответов раннера, в целях циклов, в черновике заключения, в полях заполнения сниппетов и — по желанию — в редакторе заметок.

Включите её в **Settings → Protocol Former → Текстовая автозамена**, затем откройте **Фразы для вставки**. Каждая строка — пара: слева ключ, справа вставка. Поле поиска над списком фильтрует фразы по ключу или вставке, а кнопка **Добавить фразу** добавляет новую строку в начало списка. Кнопка-иконка переключает строку между двумя режимами:

- **Автозамена** — ключ заменяется, как только он набран целиком: `-->` становится `→`. Это поведение Substitutions.
- **Вставка по хоткею** — набранное слово остаётся как есть, пока вы не выполните команду **Insert phrase from trigger** из палитры команд или по её хоткею. Наберите ключ, нажмите сочетание — слово заменится. Команда срабатывает для любой фразы, включая режим автозамены; хоткей назначается в **Settings → Hotkeys** (по умолчанию его нет).

В замене `\n`, `\t`, `\b` и `\\` — эскейпы символов, `$nl$` вставляет перенос строки, а `$end$` отмечает, куда встанет курсор после раскрытия (по умолчанию — в конец). В ключе не может быть пробелов; строка с пустым ключом или пробелом в ключе помечается как ошибочная и игнорируется.

Ограничения:

- Замена срабатывает только при прямом вводе; вставленный текст никогда не переписывается.
- Вставка по хоткею работает только в полях самого Protocol Former и в редакторе заметок. Она не может переписать поле поиска или ввод другого плагина и подчиняется переключателю **Работать в редакторе заметок**.
- В полях плагина замена обходит нативную историю отмены браузера (один Ctrl+Z не вернёт ключ). В редакторе заметок история отмены обычная.
- Список правил `ключ => замена` из 3.6.21 переносится автоматически: строки становятся фразами с автозаменой, кроме строк старого режима **По пробелу** — они становятся фразами с хоткеем.
- Если другой плагин автозамены всё ещё включён, отключите его, чтобы в редакторе заметок не было двойной замены.

## Самопроверка

В протоколе можно задать контрольный список завершения. В редакторе протокола откройте кнопку списка в плавающей панели инструментов, включите самопроверку и добавьте пункты. После последнего вопроса runner покажет список вместо немедленного закрытия. Runner закроется, когда отмечены все пункты, — если только в черновике заключения не остался невставленный текст.

## Библиотека сообщества

Библиотека сообщества позволяет просматривать и устанавливать опубликованные протоколы, не выходя из Obsidian. Каталог и модерация обеспечиваются внешним сервисом, а не этим репозиторием: Protocol Former является клиентом, а не хостингом реестра.

Protocol Former поставляется со встроенными адресами каталога (`https://library.radiprotocol.pro`, зеркало `https://radiprotocol.pages.dev`), поэтому библиотека работает без настройки. Явный адрес в **Advanced → Library registry URL** заменяет встроенные адреса; оставьте поле пустым, чтобы использовать их. Некорректное или не-HTTPS значение делает каталог недоступным.

Если реестр недоступен, представление библиотеки показывает баннер недоступности и, при наличии, последний кэшированный каталог.

### Установка пакета

1. Запустите **Open community library**.
2. Просматривайте каталог, используйте поиск или фильтр, затем откройте пакет и проверьте название протокола и пути сниппетов вместе с их SHA-256-хэшами.
3. Нажмите **Install**. Protocol Former повторно загружает полный релиз, проверяет хэши и граф протокола, затем фиксирует сниппеты, протокол и в последнюю очередь маркер установленного пакета.
4. Дождитесь результата в окне прогресса. Пакет появится в разделе **Installed**, а протокол — в обычных списках выбора после того, как Obsidian проиндексирует новый файл.
5. Если окно сообщает, что индексация ещё не завершена, пакет уже зафиксирован; не устанавливайте его повторно. Протокол может вскоре появиться в списке выбора. Обновите представление библиотеки, чтобы проверить запись в разделе **Installed**.

Файлы установленных пакетов находятся в управляемом пространстве `library/<package>/<version>/` внутри настроенных папок протоколов и сниппетов. В Protocol Former они доступны только для чтения; используйте **Uninstall** в разделе **Installed**, чтобы удалить только файлы пакета.

**Import from file…** устанавливает JSON-пакет из хранилища через ту же проверку и тот же транзакционный путь. Это удобно для офлайн-обмена и для проверки пакета перед публикацией.

### Публикация пакета

**Export protocol as library package** открывает окно экспорта для выбранного протокола. Есть два пути:

- **Save to this vault** сохраняет пакет как JSON-файл в выбранную папку.
- **Send to the Community Library** отправляет пакет на модерацию.

Для отправки нужно явно подтвердить, что пакет может быть опубликован публично и что вы владеете правами на его распространение. Библиотека сообщества публична: не добавляйте данные пациентов и реальные идентификаторы случаев. Каждую заявку проверяет модератор; плагин сохраняет заявку локально и показывает ссылку на PR модерации.

Раздел **My submissions** в библиотеке показывает заявки, отправленные из этого хранилища. Это локальный учёт, а не синхронизация аккаунта. Кнопка **Check status** сверяет заявку с реестром, **Retry** повторяет неудачную или неопределённую попытку, **Delete record** удаляет только локальную запись и не затрагивает PR модерации.

> **Граница доверия.** SHA-256 подтверждает, что загруженное содержимое совпадает с манифестом релиза. Проверка **не** удостоверяет издателя и не доказывает авторство пакета.

## Создание протокола

1. Запустите **Open protocol editor**.
2. Создайте или откройте `.rp.json` файл в настроенной папке протоколов. Новые протоколы уже содержат узел Start.
3. Добавьте клинические узлы **Question** и соедините их с узлами **Answer** или другими узлами протокола.
4. Соединяйте узлы **Answer** цепочками для фиксированного текста заключения (`Question → Answer1 → Answer2`): выберите Answer1, чтобы добавить его, а последующий Answer2 добавится автоматически без ещё одного нажатия.
5. Используйте **Snippet** для вставки повторно используемых фрагментов из файла или папки.
6. Используйте **Loop**, если один и тот же раздел может повторяться.
7. При необходимости задайте контрольный список самопроверки в панели инструментов редактора.
8. При необходимости задайте преднастроенный черновик заключения кнопкой с карандашом в панели инструментов редактора; его строки будут заполнять черновик Runner при каждом новом запуске.
9. Сохраните протокол и проверьте его командой **Run protocol** на Markdown-заметке.

> **Совместимость текстовых блоков.** В новых протоколах узел **Text block** больше не предлагается в меню создания — вместо этого соединяйте узлы **Answer** цепочками. Существующие протоколы с узлами `text-block` (включая с привязкой к сниппетам) продолжают загружаться, выполняться, редактироваться и отображаться в **Start from specific node**; их не нужно мигрировать.

## Сниппеты

Protocol Former поддерживает два формата сниппетов в виде `.md`-файлов в папке сниппетов:

- **Обычные Markdown-сниппеты**: содержимое файла вставляется как есть, без подстановки плейсхолдеров.
- **Markdown-шаблоны**: `.md`-файл с YAML-подобным frontmatter, в котором объявляются плейсхолдеры. Поддерживаются типы **свободный текст** и **выбор** (с необязательными предопределёнными вариантами). Плейсхолдеры заполняются во время выполнения протокола и подставляются в тело шаблона через токены `{{id}}`.

Узел сниппета может ссылаться на конкретный файл или на папку. Если выбрана папка, runner во время выполнения предложит выбрать один сниппет из этой папки.

> **Устаревшие JSON-сниппеты.** В старых версиях сниппеты хранились как `.json`-файлы. Эти файлы **не конвертируются и не удаляются** — они остаются на диске, но больше не отображаются в списках, не ищутся и не вставляются. Чтобы продолжить использовать их содержимое, пересоздайте их как Markdown-шаблоны с frontmatter и обновите ссылки на сниппеты в протоколах.

## Где лежат данные

- Файлы протоколов лежат в настроенной **Protocol folder**, сниппеты — в **Snippet folder**.
- Установленные пакеты библиотеки лежат в `library/<package>/<version>/` внутри этих папок.
- Служебные данные библиотеки (записи об установке, кэш каталога, заявки, журнал транзакций) лежат в `.radiprotocol/library/`.
- Настройки плагина лежат в `.obsidian/plugins/radiprotocol/data.json` и управляются Obsidian.

Резервное копирование выполняется обычным копированием хранилища; отдельной базы данных у Protocol Former нет.

## Для контрибьюторов

Требования: Node.js 22 и npm.

```bash
npm ci
npm run build   # строгая проверка TypeScript, затем production-сборка
npm test        # тесты Vitest
npm run check   # сборка, lint, тесты, проверки planning/consistency/agent-docs
npm run check:release  # check + аудит CSS-классов и i18n UI-текста
```

Для живого dev-хранилища скопируйте `.env.example` в `.env` и укажите `OBSIDIAN_DEV_VAULT_PATH`. `npm run dev` следит за исходниками и копирует `main.js`, `styles.css` и `manifest.json` в папку плагина этого хранилища. Dev-сборка не запускает `tsc`; перед коммитом выполняйте `npm run build`.

Хуки репозитория лежат в `.githooks/` и необязательны для каждого локального клона. Чтобы включить их, выполните:

`git config core.hooksPath .githooks`

Pre-commit запускает lint для staged TypeScript/CSS и затронутые тесты Vitest. Pre-push запускает `npm run check`. Обходите хуки только при явной причине и вручную выполняйте эквивалентные проверки перед pull request.

Архитектурные заметки лежат в `.rpiv/guidance/`; обновляйте их при изменении границ слоёв. Релизные артефакты — `main.js`, `styles.css` и `manifest.json`.

Для релиза используйте `npm version X.Y.Z`, чтобы `manifest.json` и `versions.json` обновились через lifecycle версии. Git-теги числовые, потому что `.npmrc` задаёт пустой префикс тега. Отправьте тег, чтобы release workflow создал GitHub Release.
